## Work path as an evidence review — 15 October 2026

The previous Work path met a navigation goal: it preserved action positions, target identity and returns. It did not meet the research goal of making a repeated-work episode understandable without opening many units. Counts and lines alone do not distinguish a prerequisite repair from repeating an ineffective attempt.

For action-based observations, Work path now starts with **Review repeated work**. Targets are ordered by action count, with saved returns after error reports, exact dispatch comparisons and feedback coverage. A selected target shows every action, its bound feedback, the agent's saved assessment/evidence-use references, intervening work and the next recorded action. The timeline and detailed route remain alternative views of the same identities. Contribution-level observations retain their timeline; they are not reinterpreted as dispatched attempts.

The product question is: **Where did the agent spend repeated effort, what changed, and what evidence followed?** In the inspected DevAI software rollout, training commands remain identical while syntax repairs and package installations occur between calls. PDF conversion repeats an exact command and exact warning after a directory check, then repeats the command after an image-reference edit. Showing both contexts makes the comparison useful without labeling either as wasted effort or claiming recovery. Following directory-listing evidence is presented separately from the agent's claim about PDF contents.

Implementation reuses the saved `work_navigation` result, the occurrence/identity checks in `WorkTimeline`, and existing structured-output previews. `work-review.js` is a read-only UI projection over an exact graph/source/run match; it introduces no annotation protocol, database migration or model calls. Every displayed response/reference keeps its node and edge IDs. Error-return counts require an explicit `revisits_after_error_report` link between the exact recurrence endpoints. Dispatch and feedback matches use full captured strings, not truncated previews. Shared, empty and metadata-only responses cannot establish matching feedback. Disputed work groups, ambiguous route membership and unresolved endpoint order cannot produce those findings. Late references retain their actual source position rather than being presented as the reason for an earlier retry.

This is a supported review workflow, not a validated autonomous diagnosis. Target grouping and semantic links still depend on observation quality. Success, ignored feedback, unnecessary work, causal recovery and RL improvement are not inferred. The next product validation is whether researchers can identify and explain these sequences faster and with fewer mistakes than from the original trace; browser checks alone cannot establish that benefit.

## Scoped operation outcomes and repeated work

8 October 2026. `operation-outcomes/5` adds response characteristics and five source-bound transitions to the same Behavior map. A response may record a completed, failed, partial or pending operation, or fail to establish an outcome. These are scoped to the dispatched operation. A completed read can return an error log, an echo can return an unsupported success claim, an edit can write buggy code, and an API call can return a reservation without independently establishing policy compliance. None becomes verified task or Plan completion.

The pipeline is deliberately layered. First select operation mechanism using the existing delivery vocabulary and dispatch only; the response is withheld. Then reuse the exact executor-error harness to distinguish current diagnostics from returned contents. Finally select raw argmax among outcome candidates for that mechanism. When a complete readable dispatch/response has a selected `not_reported` executor-error observation, `failed` is excluded because the failed-outcome definition requires a reported current execution failure. Completed, partial, pending and not-established remain candidates. Positive error reports do not force failure: handled failures can coexist with completion. Unresolved or incomplete error evidence does not eliminate candidates. All upstream decisions, candidate constraints, raw probabilities, selected options and canonical mappings remain recorded. There is no confidence threshold or post-selection probability override. Upstream attribution mistakes can still propagate and require evaluation.

The `software-operation-outcomes`, `airline-operation-outcomes` and `retail-operation-outcomes` observers preserve the original units and existing relations. A `completed_after_failed_call` edge requires a saved same-target recurrence, an undisputed identity group, the same actor/trajectory, complete consistent response sets at both endpoints, and earlier failure feedback available before the later dispatch. The edge's cutoff is the later result, not its dispatch. Unassigned/missing identity or absent feedback does not prove a negative transition. Multiple responses that disagree, or include uninspected evidence, cannot supply a terminal endpoint. The raw choice remains visible. This represents a failure/completion sequence; it does not prove causal recovery or satisfaction of changed task terms.
