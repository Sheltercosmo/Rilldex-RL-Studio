## Review against recorded terms

The evidence dialog also offers **Review against requested terms**. Load the
terms saved in the selected graph, choose up to eight, and run the search. This
reuses existing extraction; it does not invent a new decomposition of the claim.
The `requested-evidence-review/2` projection keeps requested work, requirements,
requested checks and attributed claims distinct, with their exact source quotes
and versions. A requested check is not a passing check; a user assertion is not
an established fact.

Only versions before the selected contribution in the same recorded context are
eligible. Superseded and withdrawn versions remain visible in history. An
unreadable or unordered revision makes that record unresolved instead of silently
substituting an older requirement. Source-only graphs can still use ordinary
evidence search; their lack of saved terms is shown explicitly.

Choose **Actions and returned results** when inspecting execution rather than
repeated discussion, or retain all visible record types for communicative
requirements. The filter governs primary candidates; linked source context can
include other types. These are lexical matches, not witnesses adjudicated as
support or contradiction. The originating request is identified separately.
Every term retains `verdict="not_assessed"`; unselected terms remain unsearched.
Downloads include the selected versions, scope, open review state and all loaded
evidence pages. Existing annotations, graph relations and measurements are unchanged.
The retrieval character budget counts the nested evidence packet. The catalog,
historical terms and their definition quotes are additional metadata; the whole
review response is not a model-token budget.

## Python without export

```python
from rilldex import Workspace

workspace = Workspace("workspace.sqlite", experiment="my-experiment")
evidence = workspace.search_evidence(
    run_id,
    anchor={"event_id": "e101"},
    text="GDSC dataset",
    limit=8,
    max_chars=16000,
)
for record in evidence["records"]:
    print(record["event_id"], record["reasons"])
    for fragment in record["fragments"]:
        print(fragment["start"], fragment["end"], fragment["text"])
```

For a diagnostic with separately specified evidence needs, use the same API:

```python
evidence = workspace.search_evidence(
    run_id,
    anchor={"event_id": "e101"},
    questions=[
        {"id": "attempt", "text": "first PDF conversion failure",
         "source_types": ["action", "feedback"]},
        {"id": "artifact", "text": "later PDF file available",
         "source_types": ["feedback"]},
    ],
    strategy="source_and_calls",  # optional; default is "source"
    limit=8,
    max_chars=16000,
)
for question in evidence["questions"]:
    print(question["id"], question["status"],
          question["retained_match_event_ids"],
          question["omitted_match_event_ids"])
```

Supply 1–8 questions with distinct simple IDs, at most 2,000 characters each and
6,000 total. `limit` must be at least the number of questions. `source_types`
optionally limits primary candidates to native `action`, `feedback` or `prose`
records; linked context can contain other record types. When questions are
supplied they replace the single text query for ranking. Status values are
`candidates_retained`, `candidates_omitted`, or `no_lexical_matches`. None means
that the question is answered. `context_only_match_event_ids` identifies retained
candidates matching through recorded context rather than their own text.

Use an actual event ID from the selected rollout. Optional `start` and `end`
anchor a contribution within an event; they are Unicode code-point offsets,
with an exclusive end. Only characters before `start` are eligible within that
event. A frozen analytical export without original sources is insufficient;
use the live workspace or a restored workspace containing those records.

The registered `evidence_search` analysis operation exposes the same query through
`POST /api/investigation-plans`. Its parameters are `run_id`, exact `source_hash`,
and `query` containing the arguments above. It requires no graph or semantic
observer. The registry retains versioned results and reuses an exact query on
the same source revision. The Python method computes locally without persisting
an investigation.

### Continue with an explicit budget

Use the returned cursor with the same anchor, questions, method and budgets.
For example, this loop returns at most three pages and 48,000 source characters:

```python
query = dict(anchor={"event_id": "e101"}, text="cross validation metrics",
             limit=8, max_chars=16000)
pages = []
cursor = None
for _ in range(3):
    page = workspace.search_evidence(run_id, **query, cursor=cursor)
    pages.append(page)
    cursor = page["pagination"]["next_cursor"]
    if cursor is None:
        break
characters = sum(p["coverage"]["source_text_chars"] for p in pages)
# Review passages; do not treat candidate retention as a verdict.
```

The cursor binds the retrieval version, visible source prefix, selected anchor,
query, method and budgets. A change rejects continuation; start a new search.
Later events outside the prefix cannot reorder it. HTTP investigations also pin
the full immutable source revision. A candidate deferred by the character budget
is first on the next page rather than silently skipped. Primary event candidates
do not recur; recorded context can recur and counts toward every page's budget.
The UI shows both current-page and cumulative source characters. Form edits
take effect on **Find earlier evidence**, not when continuing a loaded search.

`exhausted` means the ranked event candidate list ended. It does not mean every
passage in those events was returned, nor that unmatched/paraphrased evidence is
absent. Character limits are not model-token limits. Each SDK page rebuilds the
local FTS index; this is single-rollout retrieval, not a distributed search service.

The cursor follows the standard principle of stable query/order during paging
described by [Elasticsearch's pagination documentation](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/paginate-search-results).
Rilldex uses its own source-bound cursor over SQLite FTS5, not Elasticsearch.

The [continuation development replay](../research/evidence-continuation-2026-10-16/README.md)
recovers all reference excerpts for 10/11 positive questions across four pages,
versus 5/11 on the first page, at 3.47 times the cumulative text cost. This measures
additional retrieval at a larger budget; it is not a fixed-budget ranking gain,
independent accuracy evaluation, or automatic answer-quality result.

## Retrieval contract and limits

- Eligible text is the earlier, agent-visible prefix of the same trajectory.
  Records must also share the anchor's recorded context and have established
  earlier order. Missing context IDs share an unspecified scope; absent session
  metadata does not prove isolation. With unresolved anchor order, only earlier
  characters in that same record can be searched. External evaluation records,
  unestablished visibility and sibling parallel dispatches are excluded. Future
  records and other recorded sessions cannot change ranking or continuation.
- [SQLite FTS5](https://www.sqlite.org/fts5.html) indexes readable 320-character
  passages at a 256-character stride, retaining surrounding 1,200-character
  windows. Each question uses the first 32 unique non-stopword tokens.
  BM25 is lexical ranking, not confidence or semantic relevance.
- Source ranking reserves up to two matches each for native action, feedback and prose
  record types, then fills remaining slots by lexical order. Defaults retain
  eight primary matches. This reduces summary domination; it does not solve
  paraphrase retrieval. Version 4 interleaves independently ranked questions
  round-robin; their BM25 scores are not compared across questions.
- Optional recorded-context retrieval uses a separate index for source-bound
  dispatch and parent text, then combines source and context event rankings with
  [reciprocal rank fusion](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf),
  with the paper's `k=60`. It does not blend model probabilities. Context text is
  capped at 1,200 readable characters per related record and 2,400 per indexed
  context field. This can miss later context. Every index uses only the visible
  prefix, so future or unrelated-trajectory text cannot affect its ranks.
- Native action/result identity and recorded parent IDs add related context; adjacent prose is labeled
  as adjacency. First and last visible user requests are context. Copied history
  remains labeled. These are not evidence that the agent understood or used it.
- `max_chars` bounds source text, not serialized JSON size or model tokens.
  Deferred fragments, omitted records and omitted characters are exposed.
  A question's retained match must include its particular matching passage;
  retaining another excerpt from that record is insufficient. Matches and paired
  context can still be incomplete. Encoded media is excluded.
- Matching passages for explicit questions are reserved before optional request,
  call and surrounding-record context. If a full surrounding window will not fit,
  the exact matching chunk may fit. `retained_match_ranges` exposes source-bound
  code-point ranges per question; for `recorded_context` matches these are the
  candidate response ranges, not proof that its own text answered the question.
  `coverage.deferred` reports the final omitted ranges and their character counts,
  even when part of the requested window was retained. Omission counts for
  overlapping reasons are not additive. Neither retention nor exhaustion is a verdict.
- No match is not evidence of absence. A contradictory snippet is not an
  automatic reward-hacking or false-completion verdict. Open originals, refine
  the question and inspect missing evidence before reaching a conclusion.

## Session boundaries and question budgets — version 6

Source search now applies recorded context and order boundaries before indexing,
including native call-context ranking, linked context and task requests. A parent
message must precede its dispatch; copied history is searchable as labeled text,
but cannot act as a native dispatch parent. The `scope` field and UI distinguish
recorded session isolation, missing context metadata and unavailable earlier order.
The cursor binds this scope. Earlier-version cursors require a new search; saved
investigation outputs remain immutable and readable.

The existing 13-question public development replay shows **no excerpt-recall gain**:
source-only remains 23/38 excerpts and 4/11 complete positive packets;
question/context retrieval remains 30/38 and 5/11 at eight matches and 16,000
characters. Four-page continuation remains 37/38 and 10/11. These are overlapping,
model-authored development references, not independent accuracy samples.

Separate authored counterexamples reproduce cross-session and unresolved-order
leakage in version 5 and show exclusion in version 6. A two-question record now
retains both matching passages within 2,000 characters, versus one previously.
This is a bounded-allocation correction, not demonstrated broad ranking improvement.
See [implementation and validation](../research/evidence-scope-budget-2026-10-16/README.md).

## Execution and probability comparisons

The [humans& simulator](https://humansand.ai/blog/nvfp4-rl?v=3) motivates aligning
execution, mismatch, gradients and outcomes; its critical thresholds are simulated.
[Prime RL v0.10.0](https://github.com/PrimeIntellect-ai/prime-rl/blob/v0.10.0/docs/ipo.md)
motivates probability-gap tails and replayed probability/ratio exclusion rules.
Rilldex now records these diagnostics from supplied token probabilities, with counts
and rule disagreement. Controlled, randomized and storage tests validate the
calculation, not optimizer superiority or real-training failure prediction.
